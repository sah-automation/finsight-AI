# ADR-0010: The metrics API serves ready-to-draw chart series and export metadata

## Status

Accepted. Consumes the `kpi_current` read view settled in ADR-0009. Owns the wire contract only; the RBAC matrix stays with #355, dashboard layout and the `Updating` signal with ADR-0011, config key names and validation with #359, and screen acceptance with #357.

## Context

#353 asked for the exact API contract the Phase 2 dashboard and Charts screen consume, plus the export payload. The issue proposed `GET /companies/{company_id}/kpis`, a fixed `chart_id` spec for `GET /companies/{company_id}/charts/{chart_id}`, a `labels`/`datasets` series shape, and client-side PNG/PDF generation from the same data.

Five conflicts had to be settled rather than silently inherited. First, ADR-0011 stores an ordered list of `chart_id`s in each saved dashboard layout, but the binding `prototype/charts.html:28-34` is an interactive builder (chart type, metric, 4/6/8-quarter range, two to four comparison periods, breakdown key and breakdown period); a fixed catalogue alone cannot express those choices. Second, the issue named `breakdown_pie`, while the binding prototype draws Breakdown as a horizontal bar chart with printed shares (`prototype/charts.js:22-28`, `prototype/charts.html:72-75`) and `UI_STANDARDS.md:453` also needs a diverging budget-vs-actual variance chart. Third, dataset-level citations and status cannot describe a series whose points come from different periods and document versions, and the prototype precomputes shares (`prototype/charts.html:56`) despite its own comment that figures are never calculated in the UI. Fourth, the issue's `data: number[]` and `dashboard-{company_slug}-...` filename conflict with `CODING_STANDARDS.md:266` (use `Decimal`, never `float`) and with the standing rule that no company data appears in filenames or logs. Fifth, the issue's `/companies/{company_id}/...` path puts a company id in the client's hands, while as-built identity comes from Cognito claims in the ASGI scope (`correlation_identity.py:43-53,101-150`), dev headers are explicitly non-authoritative (`:139-148`), and `UI_STANDARDS.md:629` says the UI never builds a company id.

The research in `docs/research/accessible-charting-export.md:602-614` settles Recharts v3 with an accessibility layer, SVG-to-canvas PNG export and client-side PDF, with no server-side rendering in Phase 2. As built there is no KPI table, port or adapter (`docs/plans/phase1/phase1_as_built_deviations.md:132`), the source-viewer routes are not mounted (`:105`), and the OpenAPI artifact and generated client are checked by `scripts/check_openapi.py:12-23` — so new routes require regeneration of `docs/openapi.json` and `web/src/generated/api.d.ts`.

## Decision

- **Both routes take the company from the authenticated context only**: `GET /kpis` and `GET /charts/{chart_id}`. There is no `/companies/{company_id}` path segment and no client-supplied company id to reconcile; this deliberately deviates from the issue's proposed URLs to follow as-built identity and `UI_STANDARDS.md:629`. Dev `x-company-id`/`x-role` headers never override ASGI-scope claims (`correlation_identity.py:139-148`).
- **`GET /kpis`** accepts repeatable `kpi_code`, `period_from`, `period_to`, `currency` and `units`, plus cursor pagination (`limit`, `cursor`) ordered by `period_start` descending. It returns rows from `kpi_current` (ADR-0009) with every ADR-0008/0009 field exposed: `kpi_code`, `period`, `period_start`, `chart_period`, `chart_period_start`, `currency`, `units`, `value`, `source_citations`, `computation_status`, `estimation_method`, `document_version_id`, `computation_rule_version`, supersession and conflict markers, `created_at` and `updated_at`. `period_from`/`period_to` filter on `period_start`; the chart endpoint buckets on `chart_period_start`. No field is hidden and no value is derived by the client.
- **Numbers go on the wire as exact decimal strings**, including derived `change` and `share` values. Missing inputs produce `null`, never a guessed number and never a JSON number coerced from a `Decimal`.
- **`GET /charts/{chart_id}`** requires a `chart_id` that resolves a config-defined baseline specification, so saved dashboard layouts keep working. Optional query overrides — `chart_type`, repeatable `kpi_code`, `period_from`, `period_to`, explicit `periods` (two to four), `breakdown_key`, `breakdown_period` — may only select values the spec's config allows. Fixed and overridden requests return the same response shape. No chart type, KPI or breakdown is chosen by a model.
- **The chart type enum is closed**: `trend_line`, `comparison_bar`, `breakdown_bar`. Budget-vs-actual variance is a `comparison_bar` with a config-driven diverging presentation flag and a `variance_rows[]` array in the response: each row carries a name and actual, budget and variance values as decimal strings plus a server-computed favourable/unfavourable flag, replacing the prototype's hard-coded strings. There is no `breakdown_pie` in Phase 2.
- **The response carries `contract_version: 1`, `chart_id`, `labels[]` and `datasets[]`.** Each dataset has `series_type` (`kpi` now; `forecast` and `anomaly` are future additive values), `label`, `currency`, `units`, `period`, a renderer-friendly `data[]` of decimal strings or `null`, and a parallel `points[]`. Each point carries its own `value`, `period`, `chart_period`, `source_citations`, `computation_status`, `display_label`, `change`, `change_direction` (`good`/`bad`, from the KPI's configured polarity), `share`, and a reason when `value` is `null`. Shares, changes and direction are computed by code, as the prototype's precomputed `SHARE` table and `up` flag imply; the client never decides which direction is good (`UI_STANDARDS.md:653`). An empty dataset is a normal 200 with empty arrays and an `insufficient_data` reason, not an error.
- **Machine status and presentation are separate.** `computation_status` remains `computed`/`estimated`/`needs_review`. `display_label` is `Draft`, `Estimated` or `Updating`, or `null` for a plain final figure: `Estimated` comes from `computation_status`, `Draft` is resolved from the source document version's status, and `Updating` is injected by the API from the ADR-0011 staleness signal and is never stored on a KPI row. If several apply, `Updating` takes precedence, then `Estimated`, then `Draft`.
- **One response feeds both rendering and export.** Each chart response includes an `export` block with a server-generated UTC `generated_at`, `company_name`, an opaque `company_slug`, `period_range`, `currency`, `units` and a `source_document_list` of document titles and versions. Titles and versions are resolved server-side because the as-built source-viewer routes are not mounted. PNG and PDF are generated in the browser from the response; there is no export endpoint and no server-side renderer in Phase 2.
- **Exported filenames carry an opaque company identifier, not a readable slug.** Use `dashboard-{opaque_company_id}-{date}.pdf` for dashboard exports and `chart-{chart_id}-{opaque_company_id}-{date}.{png,pdf}` for Charts-page exports. `company_name` appears only inside the export content. This deliberately refines the issue's `company_slug` proposal, which would have put derived company data in the filename.
- **The API filters before returning.** Each handler checks the action against the role in the authenticated context itself — it does not inherit the as-built pattern of accepting an unchecked context — then removes KPI rows, series points and `source_document_list` entries the user may not see; an export can only use what was returned. Client-side hiding is presentation, never security. The role/action matrix and `permissions.yaml` entries belong to #355.
- **Dashboard state is additive to this contract.** ADR-0011 defines `GET /dashboard/fingerprints`, which returns only per-chart content fingerprints and no figures, plus two additive fields on the `GET /kpis` envelope: `documents_processing` and `actions.upload`. The KPI list stays the single source of emptiness. Saved layouts are owned by ADR-0011 and hold only identifiers and positions.
- **No literal limits or allow-lists in code.** Page size, maximum page size, allowed chart types, KPI codes and breakdown keys, KPI polarity for `change_direction`, and the diverging flag live in config read only through the config module, in the `kpi:` section prescribed by ADR-0009 unless #359 decides otherwise. #359 owns key names, validation and both-path tests; this ADR creates no switch. `contract_version` allows later contract changes to be additive.

## Consequences

- ADR-0011 persists `chart_id`s and reads the `Updating` injection point from this contract without owning chart data. #355 guards both routes and the export action. #356 must include chart payload checks in the golden-set gates. #357 accepts screens against these shapes and the binding prototype. #359 owns the config keys named here.
- The ADR records three deliberate deviations from the issue text — `breakdown_bar` instead of `breakdown_pie`, an opaque filename identifier instead of a company slug, and context-only company identity instead of `/companies/{company_id}` URLs — so none is "fixed" by a later reader.
- Resolving `Draft` needs a source-document-version status lookup through an existing port; no new status field is stored on KPI rows. `kpi_current` remains the only read view.
- The prototype computes deltas, shares and axis scales in page scripts even though its own comments say the UI never calculates figures. The real UI must use the server-provided `change`, `change_direction`, `share`, `variance_rows[]` and `data[]` values; screen acceptance in #357 must check this.
- Implementation is future work: no KPI table, repository port or API route exists in the Phase 1 baseline. New routes must be added to `docs/openapi.json` and `web/src/generated/api.d.ts` with the generated-client check passing.
- Phase 2 tests must cover decimal-string fidelity, cursor pagination, config-bounded overrides versus a fixed `chart_id`, all three chart types including the diverging flag, per-point citations and statuses, `needs_review` nulls, empty data, server-side filtering for every role, and export metadata/filename redaction.
