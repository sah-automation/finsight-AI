# ADR-0013: Phase 2 golden cases use code-checked tolerances and a blocking dual-config gate

## Status

Accepted. Consumes ADR-0010 (chart payload and export metadata), ADR-0011 (layout, fingerprints and the `Updating` signal) and ADR-0012 (role-filtered content). Config key names remain with #359, screen acceptance with #357, and the final spec with #360.

## Context

#356 asked for Phase 2 additions to the golden set, numeric tolerances per KPI, and a release gate. Its example tolerances were starting values, and the map (#345) says the exact numbers and question mix should be sharpened "when baseline measurement is in hand". There is no Phase 2 code to measure yet: ADR-0010, ADR-0011 and ADR-0012 all record the KPI table, chart routes, layout table and fingerprint route as future work. A baseline therefore cannot be captured now, but deferring the whole decision would leave #360 with a "TBD" gate.

The as-built harness is real but narrower than the question implies. `tests/golden/questions/` holds 163 generated questions in 16 YAML files (128 with expected numbers), with fields `id`, `question`, `category`, `difficulty`, `role`, `company`, `expected` (`answer`, `numbers`, `citations`, `insufficient_data`, optional `access_denied`) and `tags`. Numeric comparison is string equality or `float` equality after stripping commas (`tests/golden/compare_results.py:90-108`): there is no per-question tolerance and no `kind`, KPI, chart or layout field. `questions/thresholds.yaml` sets `numeric_accuracy: 0.95`, `citation_accuracy: 1.0`, `answer_coverage: 1.0`, `minimum_questions: 100`, `minimum_numeric_questions: 20` and `minimum_insufficient_cases: 10`; the comparison code checks only numeric accuracy, citation accuracy, baseline drop and question-count drop. Baselines for pilot and standard are separate files with `tolerance: 0.0`, and a missing baseline currently skips the regression check. No Phase 1 question mentions KPIs, charts, dashboards, fingerprints or layouts.

CI runs `tests/golden/test_golden_harness.py` twice with different `ENVIRONMENT` values (`.github/workflows/ci.yml:314-345`), but the real ask flow lives in `run_golden.py`'s CLI; the pytest "reference answerer" tests score answers seeded from the expected results and exercise the harness, not the product. `make test-golden` is outside `preflight` and `ci`, the `v*` release workflow has no golden dependency, and `golden-live.yml`'s `LIVE_PROVIDER` flag has no code consumer. The deviations addendum records the resulting state plainly: "Golden-set release gate not machine-enforced" (`docs/plans/phase1/phase1_as_built_deviations.md:134`). The binding Config Switch Guide requires the golden set on both configs (`finsight_config_switches.md:876`), a score drop to block a speed change (`:50`, `:892`) and citation/number checks plus "insufficient data" never to be switchable (`:923-924`).

## Decision

- **Phase 2 cases are generated and kept apart.** Add the Phase 2 questions as one generated file (or subdirectory) under `tests/golden/questions/`, produced by `scripts/fixture_builder` like the existing files. The 163 Phase 1 questions and their permanent `id`s are not edited. The runner loads Phase 2 alongside Phase 1; #359's `golden_set.kpi_questions_path` points at the Phase 2 file. Hand-written cases must not live in generated files, because regeneration would clobber them.
- **Coverage counts answers and contract cases separately.** Add at least 20 new numeric KPI/chart answer questions covering all ten closed KPI codes and all three chart types (`trend_line`, `comparison_bar`, `breakdown_bar`). In addition, add tagged contract cases for chart payloads and export metadata; dashboard layout default-on-miss with no write, first save, stale-save 409 with the current layout and role-filtered ids; fingerprint stability for identical recomputes and change for document version, rule version, value, status, citation and conflict; `Updating` injection and the `Updating > Estimated > Draft` precedence; and role filtering of rows, series points, citations, layouts and fingerprint entries. Contract cases do not count toward the 20.
- **The question schema grows additively.** Keep `version: 1` and every existing field; add optional fields only — `kpi_code`, `chart_id`, `chart_type`, expected computation status and display label, expected export metadata and layout/fingerprint scenario. Answer prose is never compared. Existing question ids stay permanent.
- **Tolerances are provisional but explicit now.** Currency KPIs use `max(0.5% of expected, 1000 in that KPI's own currency)` with no conversion; margins (`gross_margin`, `net_margin`) use ±0.25 percentage points absolute; `burn_rate` and `runway` use ±5% relative; `dso` and `dpo` use ±3 days absolute; `budget_vs_actual` is an exact decimal match when both source Metrics exist and `needs_review` otherwise. A golden row expecting `needs_review` passes only when the value is `null` with that status and its display label. All comparisons are performed in code, never by a model.
- **`kpi.tolerances` is the single numeric source.** #359 defines it as a typed map covering every KPI code, with identical values in pilot and standard, validated on load and never switchable. Golden questions reference `kpi_code` rather than embedding their own tolerance. The proposed `golden_set.tolerances_file` is dropped rather than kept as a second copy that can drift; #359 keeps only `golden_set.kpi_questions_path`.
- **The baseline is recorded on first Phase 2 build, not before.** The provisional numbers above are frozen in this ADR now. When implementation lands, the first run of the expanded set on both configs is committed as the pilot and standard baselines and the blocking gate activates from that point. Baseline updates require a reviewed PR in the same change as the intended score change; a missing or unreadable baseline fails the gate instead of skipping it. The as-built drift tolerance of `0.0` stays: any drop blocks.
- **The gate is wired into PRs, main and releases.** The full Phase 1+2 set runs under both pilot and standard configs on pull requests and on main. The `v*` release/deploy workflow depends on a green main golden run rather than starting independently. Nightly/manual live-provider runs stay informational and never gate a release; the unused `LIVE_PROVIDER` flag must be wired to a real code path or removed so it cannot be mistaken for a gate. No switch may disable the gate, tolerance checks or citation/number checks.
- **Pass criteria are strict and per config.** Phase 2 KPI answers and `needs_review`/no-answer/access-denied cases must be 100% correct within tolerance; Phase 1 numeric accuracy stays at ≥95% and citation accuracy at 1.0. The gate also fails on answer coverage below 1.0, fewer than 100 total questions, fewer than 20 numeric questions, fewer than 10 insufficient-data cases, any per-config score drop or question-count drop, and any failing chart-payload, layout, fingerprint or role-filtering case. Configs are judged independently, never averaged. The currently unchecked `answer_coverage`, `minimum_numeric_questions` and `minimum_insufficient_cases` thresholds are enforced.
- **CI runs the product path, not just the harness self-test.** The gate invokes the programmatic `run_golden()` path with the deterministic adapters for every question under both configs, exercising orchestration, scoring and config loading. `test_reference_answerer_scores_perfectly` and its siblings remain harness checks; they are not the gate.
- **Export checks stop at the response.** Golden asserts that the chart response `export` block carries UTC `generated_at`, `company_name`, opaque `company_slug`, `period_range`, `currency`, `units` and `source_document_list`, that filenames use opaque identifiers with no company data, and that company names appear only inside export content. PNG/PDF rendering is accepted by #357 against the binding prototype; Phase 2 adds no server-side renderer to satisfy the gate.
- **Machine fields are the expected answer.** Golden cases assert `computation_status`, `display_label` (including `Updating` injection and precedence), exact decimal-string values, `null` values with reason strings on `needs_review`, and the absence of placeholders or counts for hidden series. No assertion matches answer prose.

## Consequences

- Three premises in #356 are deliberately not adopted as written: tolerances are frozen before a baseline exists (the baseline only calibrates the gate's activation), `kpi.tolerances` replaces a separate `golden_set.tolerances_file`, and live-provider runs do not block releases. A later reader should not "restore" any of them.
- No glossary change is needed: `golden case`, `tolerance`, `baseline` and `release gate` are harness and process concepts, not domain terms. The existing `ComputationStatus`, `Display Label`, `Export Payload`, `Dashboard Layout`, `Freshness Fingerprint` and `Role` entries already cover the domain language asserted by the new cases.
- Implementation is future work: this decision changes no code, config or infrastructure behaviour. It requires the Phase 2 implementation to extend the question generator and loader, add the typed tolerance config with both-path validation, wire the real golden path into CI and the release workflow, and commit the first baselines.
- Handoffs: #359 owns the `kpi.tolerances` type and validation and drops `golden_set.tolerances_file`; #357 accepts export rendering and the badge/empty states against the prototype; #360 writes the golden-set and release-gate section of the Phase 2 spec without a "TBD".
