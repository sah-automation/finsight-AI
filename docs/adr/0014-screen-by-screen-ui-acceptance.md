# ADR-0014: Screen acceptance follows the binding prototype, with standard-wins exceptions and machine checks

## Status

Accepted. Consumes ADR-0010 (chart payload and export contract), ADR-0011 (layout, fingerprints and the `Updating` signal), ADR-0012 (role-filtered content) and ADR-0013 (export metadata in golden cases). Settles #357. Config key names and validation remain with #359; the final Phase 2 spec remains with #360. No glossary change is needed: `Display Label`, `Export Payload`, `Dashboard Layout`, `Freshness Fingerprint`, `Role` and the Phase 1 terms already cover the domain language, and snapshot/token parity are process concepts.

## Context

#357 asked for acceptance criteria for every Phase 1 and Phase 2 screen so an implementation session can verify against `prototype/` without ambiguity. The prototype is the binding visual source (`prototype/README.md:3`), `UI_STANDARDS.md` owns behaviour and accessibility, and the parent plan owns phase scope; `AGENTS.md` and `docs/plans/phase1/phase1_as_built_deviations.md:9` require conflicts to be stopped and escalated rather than silently resolved.

Fact finding exposed real disagreements:

- The prototype has nine HTML files with a different split from the ticket's nine screens: Recycle bin is a segmented view in `documents.html`, the source viewer is a panel in `ask.html`, and `reports.html`/`not-allowed.html` are user additions with unresolved phase assignment (`UI_STANDARDS.md:242-258`, `:707-722`).
- The ticket requires an MFA prompt, pagination, a full-screen expanded chart, Draft/Estimated/Updating badges and a citation list, none of which are drawn as described. `login.html` has no MFA state, `documents.html` has no pager, `charts.html` is a builder plus chart card with `Image`/`PDF`, and `dashboard.html` draws only the `Updating` badge with a 480px metric drawer.
- `--text-muted` on `--bg-subtle` computes to 4.39:1, below the 4.5:1 AA floor the standards require, while `UI_STANDARDS.md` says to port the prototype tokens as-is.
- The source-viewer GET handlers exist but are not mounted, the as-built route is `/sign-in` rather than `/login`, and System Admin has no document `read` rather than the prototype's details-only view (`phase1_as_built_deviations.md:105,113-114`).
- `UI_STANDARDS.md` still carries open decisions for Settings, inline Ask charts, permanent delete, notification channels and source-viewer extras, and §7.6 allows a permission action to be disabled with a tooltip, which conflicts with the ticket's "absent, not just disabled" rule.
- The research recommends Recharts v3 + Tremor, `vitest-axe`, Playwright and `@axe-core/playwright`; only `vitest-axe` and two screen-level axe tests exist today. The approved messages table already has the Stop result but has no string for "Still working" or the two new dashboard states.

The user settled every branch of the decision tree in two grilling rounds. This ADR records those answers. The baseline `make preflight` was green before any edit: 188 architecture tests (1 skipped), 982 unit tests, lint, types, import rules and bootstrap parity.

## Decision

- **Scope is the nine functional screens, not nine files.** Accept Sign-in, Upload, Documents library, Recycle bin, Ask, Source viewer, Settings, Dashboard and Chart detail. Recycle bin stays a Documents view and the source viewer stays an Ask panel; the app shell and Access Denied are accepted once as cross-cutting requirements. `reports.html` is design reference only and is not part of Phase 2 acceptance; #360 records its final phase placement. All five Settings panes are in scope with the prototype's role visibility: Profile and Notifications for all roles, Users for System Admin, Audit log for System Admin and Audit & Compliance, Cost view for System Admin and Executive Leadership. An unknown Settings section falls back to Profile.
- **As-built conflicts win where the visual source describes behaviour that does not exist.** The sign-in route is `/sign-in`, not `/login`. System Admin is denied Documents as well as all financial content; the prototype's "file details only" notice is not implemented. `UI_STANDARDS.md` is corrected in the same change. Both are listed as deviations from the visual source.
- **Visual acceptance is token and structure parity plus human review, not a pixel threshold.** The app takes colours, type and spacing from the one shared token file with `prototype/styles.css` as the source; a test in `web/test/` reads that file and fails if the app's values differ. All copy comes from the messages file. Layout, component order and the four states (loading, empty, error, success) match the prototype. Approved snapshots at 390, 768 and 1280 are committed under `web/snapshots/` with an `APPROVALS.md` entry naming the approver, date and browser for each screen. Where the prototype breaks a standard, the standard wins and the difference is listed: skip link, focus trapping, focus ring, touch targets and the failing muted-on-subtle pairing. `--text-muted` is never used for normal text on `--bg-subtle`; use `--text-secondary` there. No raw colour, font or spacing value is hand-copied into components.
- **Allowed differences are recorded up front.** Real API data replaces sample numbers, sample labels and prototype-only controls; API capabilities replace the `can` table and `sessionStorage` role; accessibility fixes and the standard-wins exceptions above apply; email-only notifications replace the prototype's Push column and "Mentions" event; an API-driven pager replaces the prototype's unpaginated list; MFA and the states marked "specified by standard, not drawn" have nothing to compare against in the prototype. Nothing else counts as an allowed redesign.
- **Permissions decide presence, not presentation.** If the API does not grant an action, its control is absent from the DOM, not disabled and not merely hidden by CSS. Disabled state is reserved for non-access reasons such as Save before a change, a form awaiting required fields, or sign-in during an outage. Pages decide from the API's capability list, never from a role name in the component. A direct visit to a forbidden URL shows the approved "You don’t have access to this." message. A test per role asserts the forbidden controls are missing from the rendered page.
- **Citation acceptance has a backend prerequisite.** The source-viewer GET handlers must be mounted and must enforce company, role and access scope before any citation-click test counts as passing; a UI-only panel is not acceptance. The cited version is shown, never silently swapped. "No longer available" and "no access" are the same non-leaking screen so a deleted source cannot be distinguished from one the user may not see. "Open full document" appears only when the API grants it. The panel is a 480px column above 1180px, a floating panel from 901 to 1180px and a bottom sheet at 900px and down; `UI_STANDARDS.md §7.3` and `§13` already specify this, so no edit is needed there. At each width, `Esc` closes, focus returns to the citation chip, and the sheet traps focus.
- **Ask states are individually tested.** Show status and skeleton within 100ms, append whole verified sentences only, and keep "no unverified or partial sentence" as its own test. A check that fails after the first sentence keeps the shown sentences and adds a plain ending message. "Waking up, please wait." appears only after 2 seconds and "Still working on your question." at 8 seconds, verified with a fake clock; both clear when the answer arrives. Stop keeps sentences already shown, allows nothing half-written afterwards, reads "Stopped. Ask again or rephrase." and re-enables the question box. Insufficient data shows no red and no citations, permission denied gives no hint of what exists, and no state ever shows a raw error. Run each state for every role it can happen to and assert copy comes from the messages file. §12 already has "Stopped. Ask again or rephrase." and keeps it verbatim; §12 gains exactly "Still working on your question.", "Figures are being prepared." and "The layout changed elsewhere. Check the current layout and save again to reapply." for the dashboard.
- **Dashboard labels come from the API.** Show the badge whenever `display_label` is non-null, with `Updating > Estimated > Draft` precedence from ADR-0010; the prototype's `Updating`-only drawing is not the ceiling. The top warning appears when any visible chart is stale, a stale chart keeps its figures until interaction or reload, and there is no visible refresh control. Empty states are "Figures are being prepared" when `documents_processing` is true, otherwise "No figures yet" with Upload only when `actions.upload` is true. A stale layout save returns the current layout with the inline "layout changed elsewhere" notice, not a modal. Inline Ask charts are accepted in Phase 2 only when the answer response carries a chart payload; the client never invents one.
- **The charts page is the chart detail view.** The ticket's separate full-screen expanded chart is not adopted: `/charts` is the detail view, dashboard expansion navigates there with the selected `chart_id`, `Image` and `PDF` stay only where the prototype places them, and the source caption plus source row is the citation list. The 480px dashboard metric drawer remains as drawn. No prototype change or new full-screen route is authorised. Chart values, changes, shares and variance rows come from the API; every chart has a table fallback whose numbers, units and periods match the chart when read out.
- **Sign-in and document lifecycle follow the prototype except where already settled.** Cognito SRP sign-in keeps the three drawn states plus the approved copy; the MFA challenge for System Admin and Executive Leadership is provider-hosted and recorded as "specified by standard, not drawn", with no new app screen. Upload keeps the New/Update segmented control, duplicate warning, partition-missing replacement, per-file progress and validation; Delete stays in the Documents drawer. Delete permanently is kept for the upload-capable roles shown in the prototype, with the drawn confirmation dialog and toast, and the backend must enforce it before the button renders: reuse the existing `delete` category action only if it covers permanent purge, otherwise a dedicated action must be defined by #359/#360 first. System Admin never sees the button. Documents and Recycle bin keep the filters, sort and drawer from the prototype and gain an API-driven pager styled with existing tokens.
- **Export acceptance uses the API contract, not the prototype scripts.** PNG and PDF are generated in the browser from the ADR-0010 response. Assert UTC `generated_at`, company name, opaque identifier, period range, currency, units and source list in the export content, and opaque filenames with no company data. The prototype's title-based filename and `window.print()` PDF are implementation illustrations, not acceptance; Phase 2 adds no server-side renderer.
- **The verification gate has two automated levels and a written manual level.** Component `vitest-axe` and screen `@axe-core/playwright` checks allow zero serious or critical violations. Every screen gets a keyboard-only walkthrough, a chart table-fallback check with real data, and contrast checks for chart colours and the evidence highlight; series are never distinguished by colour alone. One written manual pass per screen uses NVDA + Firefox for desktop and VoiceOver + Safari on iOS for the phone sheet, recording tester, date, browser and screen reader so a serious finding blocks that screen and the pass can be repeated after major changes. The claim is "aims for WCAG 2.2 AA, checked by these tests", not formal conformance without an audit. Missing libraries, the width sweep, touch tests and snapshot harness are implementation work, not reasons to weaken the gate.

## Consequences

- The prototype is not edited. Its deliberate deviations are now explicit: Reports excluded, as-built `/sign-in` and System Admin denial, email-only notifications, API-driven pager, provider-hosted MFA, absent permission controls, standard-wins accessibility, API-driven dashboard labels and export metadata, and the charts page as the detail view. A later reader should not "restore" the ticket's full-screen chart or the prototype's Push column.
- `UI_STANDARDS.md` is updated in the same change: §6 route and Reports phase, §7.4 permanent delete and System Admin, §7.6 absent-permission rule, §9 dashboard/chart notes, §12 messages, §18 verification, and the decided rows of §21. §7.3 and §13 were already aligned and are left alone.
- No code, config, infrastructure or prototype behaviour changes here. Implementation still needs the source-viewer routes mounted, the permission actions and web enum updated, the token-parity test and snapshot harness added, the chart/a11y libraries installed, and the per-role and per-screen tests written.
- Handoffs: #359 owns any new permission or config values needed for permanent purge and keeps the five ADR-0012 actions in the `Action`/`PermissionAction` enums with no new switch; #360 writes the screen-acceptance section of `docs/plans/phase2/phase2_spec.md` with these criteria, the standard-wins differences and the source-viewer prerequisite, and leaves no "TBD".
