# ADR-0012: Dashboard and chart access is role-action gated and content-filtered

## Status

Accepted. Consumes ADR-0010 (metrics API and export contract) and ADR-0011 (dashboard layout and staleness). Config key names, enum values and validation stay with #359; screen acceptance with ADR-0014 (#357); the final spec with #360.

## Context

#355 asked to extend `config/permissions.yaml` with five Phase 2 actions and confirm a role matrix so every dashboard/chart endpoint is guarded. Its text also asserted that dashboard/chart responses are cached per role and that the API Gateway authorizer plus BFF middleware enforce the matrix before a handler runs. Both assertions disagree with the as-built system.

`permissions.yaml` holds four roles, six document categories and two action shapes: `categories.<category>: [actions]` and `role_actions: [actions]`. It has no KPI category, and none of ADR-0008, ADR-0009 or the code defines a KPI-to-category mapping — `Metric.category` is an untyped string from a separate `Category` enum, not a `DocumentCategory`. The answer cache is keyed by company, role, sorted access scope, question and document stamp (`cache_key.py:9-26`); there is no dashboard, chart or KPI handler, response cache or fingerprint cache anywhere in the Python source. `compute.py:204-218` installs a JWT authorizer that authenticates but maps no actions, `CorrelationMiddleware` performs no RBAC, and there is no generic per-route permission dependency — the source viewer's `AuthorizeStep` is the only direct consumer of `PermissionPolicy`. That policy still contains a legacy `permissions.get('default')` fallback and a `'*'` allowance despite the config's "No wildcards, no defaults" rule. Finally, `current_user.py:9-38` already returns `permissions`, `permission_actions`, `actions`, `role_actions` and `category_permissions`, which the web reads for navigation, so a second capability surface would be redundant.

## Decision

- **The five actions are role actions.** Add `dashboard_view`, `dashboard_edit_layout`, `chart_export`, `kpi_view` and `kpi_export` to each role's `role_actions` in `permissions.yaml`; leave the six Phase 1 categories exactly as they are and add no `kpi` category and no new top-level section. The matrix is: executive leadership and corporate finance planners get all five; audit & compliance gets `dashboard_view`, `chart_export`, `kpi_view` and `kpi_export` but not `dashboard_edit_layout`; system admin gets none and receives access denied on financial content (risk 24). "Read-only" for audit means only layout editing is withheld — there is no KPI or chart edit action. Export is read-shaped and can only use content that the response already contains, so granting it to audit does not widen access.
- **One action map guards each surface.** `dashboard_view` guards the dashboard shell, saved-layout reads and `GET /dashboard/fingerprints`; `dashboard_edit_layout` guards layout saves; `kpi_view` guards both `GET /kpis` and `GET /charts/{chart_id}` — there is no sixth `chart_view` action. `chart_export` and `kpi_export` are not endpoints: the five actions flow through the existing current-user `permission_actions`/`actions` surface, which is where the prototype's export buttons and navigation read them. `GET /kpis` keeps exactly `actions: { upload }` from ADR-0011, true only when the role holds `upload` on at least one document category (today: planners only). No export flags are added to the chart response and no new endpoint is introduced.
- **KPI visibility follows the cited document, not a KPI category.** `kpi_view` grants the closed KPI catalogue; the handler then removes KPI rows, series points and `source_document_list` entries whose cited source document's `DocumentCategory` the role may not `read` or that fall outside its `access_scope` — the same rule `AuthorizeStep` applies today. No KPI category column, KPI-to-category mapping or new category is added. A partly visible chart keeps its visible series and points; hidden KPIs leave no placeholder, count or other hint. If no KPI remains visible, the chart response is a normal empty dataset with an `insufficient_data` reason, and that `chart_id` is omitted from layout reads and fingerprint responses so the page never renders an empty or forbidden chart.
- **Layouts are filtered on both read and save.** A saved layout is keyed by `(company_id, user_id)` and holds no role, so a later role change must not resurface ids that were once hidden. Reads drop KPI codes and `chart_id`s the role may not see and skip ids unknown to config; saves drop those ids before persisting instead of rejecting the request. If nothing remains, the config default is used. A stale `version` still returns 409 with the current layout.
- **Two enforcement points, fail-closed.** API Gateway stays authentication-only. Phase 2 adds one shared permission dependency invoked at the start of each dashboard/chart handler, before data access, and each handler re-checks the action and filters the content it returns — client-side hiding is never security. Unknown role or action is denied; no wildcard and no default is used, and implementation removes the legacy `default`/`*` paths in `PermissionPolicy` rather than extending them. There is no new BFF middleware layer: the ticket's "BFF middleware" is read as this shared dependency.
- **No dashboard/chart cache in Phase 2.** Each request reads `kpi_current` through the handlers, consistent with ADR-0011's decision against a fingerprint cache. The answer cache key is unchanged. If a cache is introduced later, its key must include company, role, access scope and document stamp, and an entry must never be reused across roles.
- **Handoffs.** #359 adds the five values to the `Action` enum (`core/types/__init__.py`) and the web `PermissionAction` union, updates the hard-coded matrix and action validation in `tests/security/test_permissions.py`, and regenerates `docs/openapi.json` and `web/src/generated/api.d.ts` if the enum is published in the schema — with no new switch. #360 states that KPIs are not a category, that dashboard/chart responses are not cached, and that enforcement is JWT authentication plus handler checks. No new glossary term is needed: `Role`, `Export Payload` and `Dashboard Layout` already cover the domain language, and "action" is a config token.

## Consequences

- Three assertions in #355 are deliberately not adopted: per-role dashboard/chart caching, an RBAC-enforcing API Gateway authorizer plus BFF middleware, and a KPI category derived from document categories. None existed as built; a later reader should not "restore" them.
- Phase 2 tests must cover every role/action pair, both document-category and access-scope denial, partly and fully invisible charts, filtered layout reads and saves with the 409 path intact, upload derivation per role, and fail-closed behaviour for unknown roles and actions.
- This adds no code, config or infrastructure behaviour. Implementation is future work; the existing flaky metering test (`test_dynamo_metering.py::test_writes_one_row_per_idempotency_key`, caused by module-level `_TABLES` state) is out of scope and was recorded as a baseline flake, not fixed here.
