# ADR-0011: Dashboard layouts live in Aurora and staleness is derived from content

## Status

Accepted. Consumes ADR-0008 (KPI rows), ADR-0009 (materialisation and the `kpi.recomputed` event), ADR-0010 (chart wire contract) and ADR-0012 (role/action matrix and content filtering). Owns the saved layout model, the `Updating` signal and the update cascade; golden-set gates are settled in ADR-0013, config key names stay with #359, screen acceptance with ADR-0014 (#357) and the final spec with #360.

## Context

#354 proposed a per-company, per-role preference document in DynamoDB keyed `company_id#role#layout_v1`, with `last_refreshed_at` and `source_kpi_versions` stored per chart, event-driven invalidation and a 30-second poll. Three facts change that shape. First, `infra/cdk/stacks/data.py:159-163,267-269` states that DynamoDB holds rebuildable views and caches only, with Aurora as the source of truth; a saved layout is user-authored and cannot be rebuilt from anything else, so it is real data. Aurora also supplies backups, the company partition and a row-level lock. Second, there is no `kpi_version` field anywhere in the code or schema; `kpi.recomputed` appears only in ADR-0009, and the as-built publisher is best-effort in-memory with no durable retry or outbox (`src/finsight/adapters/messaging/change_event_publisher.py:145-177`, `src/finsight/domain/value_objects/change_event_type.py:9-31`). An event that mutates layout rows would make a lost, repeated or out-of-order delivery show the wrong badge. Third, the binding prototype has a fixed KPI grid, two trend cards and a budget-vs-actual card with no saved arrangement or refresh control (`prototype/dashboard.html:60-142`), while `UI_STANDARDS.md:450-455` supplies the top warning notice and "Updating, figures may change" badge and `:88` forbids company data in browser storage. ADR-0010 defines `Updating` as an API-injected display label with precedence over `Estimated` and `Draft`; it does not define where the signal comes from.

## Decision

- **The layout is source-of-truth data in Aurora, not a DynamoDB view.** A new `dashboard_layouts` table is keyed by `(company_id, user_id)` and nothing else: a person's arrangement must survive a role change, and both identifiers come from the authenticated context, never the page. A missing row returns the config-defined default layout; opening the dashboard never writes a row. No audit entry is required for a layout save. `dashboard.layout_store` is dropped from #359: there is no second store path and no switch for the store.
- **A layout holds only identifiers and positions.** Columns are `contract_version`, an ordered list of KPI codes from ADR-0008's closed ten, an ordered list of `chart_id`s that resolve to config-defined chart specs (ADR-0010), a bounded `span` hint per chart (`full` or `half`, from a config allow-list), an integer `version` and `updated_at`. Order is implied by the lists. No figures, displayed timestamps, `last_refreshed_at`, fingerprints, pixel coordinates, KPI/period/currency values or builder-override snapshots are stored. A user-built chart must be registered as a config spec before it can be saved. On read, ids the role may not see are filtered out (ADR-0012) and unknown ids from config drift are skipped; if nothing remains, the config default is used.
- **Saves are optimistic, immediate and non-destructive.** The page sends the `version` it loaded; a save succeeds only through a conditional update that checks that version and increments it by one. The first save succeeds only if no row exists yet. A stale version is rejected with 409, a clear "layout changed elsewhere" message and the current layout in the response, so the user can reapply the change instead of silently overwriting someone else's. There is no confirmation modal.
- **The KPI version is a content fingerprint, derived on read.** Add `computation_rule_version` as a column on KPI rows, populated from config at compute time, and expose it through `kpi_current` and `GET /kpis`. For each chart spec, hash the winning rows' `kpi_code`, `period`, `chart_period`, `document_version_id`, `computation_rule_version`, exact decimal value, `computation_status`, `source_citations` and conflict/supersession markers, sorted canonically. Exclude `created_at`/`updated_at` so an identical recompute does not produce a false `Updating`. The fingerprint is a derived view expression: not a stored counter, not a layout column and not a cache. No fingerprint cache, SSE or WebSocket is introduced in Phase 2.
- **A lightweight route carries the signal.** `GET /dashboard/fingerprints` returns `{ contract_version: 1, charts: { [chart_id]: "<fingerprint>" } }` for the signed-in company, filtered by role, with no figures, citations, document names or other company content. It resolves chart specs exactly as `GET /charts/{chart_id}` does. The page compares the returned fingerprints with those it loaded in memory; a mismatch makes ADR-0010 inject `Updating` for that chart, and the prototype's top warning notice appears when any visible chart is stale. `display_label` precedence stays Updating, then Estimated, then Draft. The route needs OpenAPI and generated-client updates like #353's routes.
- **Polling never fetches chart data.** `dashboard.auto_refresh_seconds` comes from config (#359: default 30, minimum 5, maximum 300) and governs fingerprint polls only; polling pauses while the tab is hidden. A stale chart keeps its previously loaded figures and shows `Updating`; full data is fetched only on user interaction — opening a KPI drawer, expanding a chart, changing period/range or reloading the page. There is no new visible refresh control: the binding prototype has none, so manual refresh is re-navigation/reload. A visible control would require a prototype change and ADR-0014 acceptance; ADR-0014 confirms that no control is added.
- **The event is a hint, never the truth.** After commit, `kpi.recomputed` is emitted from the outbox required by ADR-0009; This ADR consumes it only as an in-process invalidation hint if a fingerprint cache is added later. A lost, duplicated or out-of-order delivery can only delay the badge to the next poll, never corrupt it. The outbox remains necessary for other consumers; this ADR does not remove that requirement.
- **The KPI list remains the single source of emptiness.** Reuse `GET /kpis?limit=1` with no filters; no status route is added. Its response envelope gains `documents_processing: boolean`, true when any document version for the company is in `received`/`stored`/`processing` (no titles or ids exposed), and `actions: { upload: boolean }`, resolved from the authenticated role's permission matrix (ADR-0012). With zero rows, `documents_processing: true` shows "Figures are being prepared"; otherwise "No figures yet" with Upload shown only when `actions.upload` is true, else "Ask your finance team to upload documents." No polling and no layout write happen while empty.
- **Cascade end to end:** document update → Metric re-extraction → KPI recompute in the ingestion transaction (ADR-0009) → `kpi.recomputed` after commit as a best-effort hint → next fingerprint poll observes a changed view → `Updating` on the affected charts → full data on user interaction. Missing inputs remain `needs_review` with `null` values; risk-28 conflicts keep both cited rows and change the fingerprint through their stable fields.

## Consequences

- This deliberately supersedes three parts of #354's proposal: Aurora instead of DynamoDB, per-user instead of per-role, and no `last_refreshed_at`/`source_kpi_versions` in the layout; the event never writes a stored row. It also replaces #359's `layout_store: dynamodb` key and #360's "dashboard layout in DynamoDB" spec line. Recorded here so a later reader does not "restore" the original plan.
- ADR-0008 gains `computation_rule_version` on KPI rows; ADR-0009's rebuild gating already uses that version, and ADR-0010's wire contract gains one route and two additive `GET /kpis` envelope fields. ADR-0012 owns `dashboard_view`/`dashboard_edit_layout` and requires the API to filter saved ids before returning a layout; ADR-0013 settles fingerprint and layout cases in the golden-set gates; ADR-0014 (#357) accepts the top notice, badges and empty states against the binding prototype with no added refresh control.
- Phase 2 tests must cover: default-on-miss without a write; first save with no row; concurrent save rejection with the current layout returned; role filtering of both saved ids and fingerprint entries; fingerprint stability for identical recomputes and change for document version, rule version, value, status, citation and conflict changes; lost, repeated and out-of-order events still yielding a correct badge; in-memory fingerprint comparison across loads; empty, processing and permission-denied upload states; fingerprint-only polling with no chart data; and OpenAPI/generated-client regeneration.
- Implementation is future work: no layout table, port, adapter, fingerprint route or KPI table exists in the Phase 1 baseline. No code, config or infrastructure behaviour changes in this decision.
