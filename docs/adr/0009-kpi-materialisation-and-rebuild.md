# ADR-0009: KPI rows are committed with their source version and rebuilt by rule version

## Status

Accepted. Refines the storage key in ADR-0008; ADR-0008 remains the accepted domain model.

## Context

ADR-0008 settled what a KPI row means but left materialisation, estimation mechanics and rebuilds to #352. Its four-column key cannot distinguish the three monthly rows spread from one quarterly source, and #352's draft `source_version` key does not exist in the codebase. The Phase 1 ingestion commit already writes document versions, chunks, vectors, Metrics, the document stamp and change events in one transaction, but it publishes the event before commit and has no KPI layer (`src/finsight/application/ingest_document/pipeline_step_worker.py:1446-1729`). No `kpi:` config section exists; the typed `scale` defaults are not in any shipped YAML, and `Reprocess` defaults to `low`, which maps to waiting-line rank 1 rather than the `reprocess` rank (`src/finsight/adapters/waiting_line/waiting_line_settings.py:11-22`, `:109-115`). Risk 28 requires final > draft, newer > older, and both cited rows shown when figures still differ (`docs/plans/project_requirement/finsight_known_risks.md:850-875`). The Config Switch Guide requires fail-loudly config, both paths tested and one config change per release (`docs/plans/project_requirement/finsight_config_switches.md:38-51`).

## Decision

- KPI values are computed by pure code from Metrics; the model never authors or edits them. Materialisation happens during ingestion: computed KPI rows are upserted in the **same transaction** as chunks, vectors, Metrics and the document stamp. A failed commit leaves neither KPI rows nor an event.
- The `kpi.recomputed` invalidation event is emitted **after commit** through an outbox/after-commit mechanism. It carries `company_id`, affected `kpi_code`s and periods, `document_version_id`, `computation_rule_version`, and lineage/conflict markers. Dashboard staleness, the `Updating` badge and refresh polling stay with #354.
- With `documents.delta_tracking: true`, compare the figures extracted for the new version against those of the previous version and recompute every KPI that depends on a changed, added or removed figure, including indirect dependencies from a changed figure even when the dependent figure sits in an unchanged chunk. Removed figures count as changes. With `delta_tracking: false`, re-extract all figures and recompute every KPI for the new version. Both paths must produce identical final KPI rows; a test runs the same update through each and compares results.
- KPI rows live in one KPI table; no separate stored monthly table is introduced. The storage key is amended to `(company_id, kpi_code, period, document_version_id, chart_period)`, replacing the four-column key in ADR-0008. `chart_period` is non-null and equals `period` for non-estimated rows. `period` remains the source-declared text label. `period_start` is a DATE used for range filters and ordering; estimated rows also carry `chart_period_start`. Dates are derived from the text label in code and checked for agreement so the two cannot drift.
- Monthly partitioning is **not** added in Phase 2: Phase 1 already gives each company its own partition and a quarterly row has no single month. If a load test later shows a need, partition by company first and use `period_start` inside that partition.
- `superseded_by_document_version_id` is a stored lineage field set **only** for same-document history: a newer version of the same document takes over, the latest final version is used, and the old version stays viewable. No `conflict_group_id` is stored. A conflict is derived on read by checking whether different documents still show different numbers for the same company, KPI and period; a view-only computed id may be exposed for UI grouping. Neither mechanism changes `computation_status`. Retention still applies: rows go away under `version_retention_days` and `deleted_retention_days`, so "not deleted" does not mean kept forever.
- `kpi_current` is the single read view for the metrics API defined in ADR-0010. It applies final > newer selection, shows both cited rows when figures still differ, and exposes `superseded_by_document_version_id` only as history.
- Estimated monthly rows are stored in the KPI table with `computation_status: estimated`, an `estimation_method` from a fixed allowed list initially containing `quarterly_spread_equal`, and their own `chart_period`/`chart_period_start`. `kpi_current` normalises them for charts; the `Estimated` label is never presented as a source-stated figure.
- KPI computation/estimation rules and rebuild controls live in a `kpi:` config section read only through the config module. Missing or unknown values stop startup. `estimation_method` is a fixed enum starting with `quarterly_spread_equal`; `rebuild_batch_size` must be positive. `rebuild_priority` accepts only the named ranks `rebuilds` and `background`, mapped below live questions and uploads, with startup validation rejecting live/upload values for this key and asserting that rebuilds always rank below live questions.
- Changing `computation_rule_version` is blocked unless the rebuild for that version is marked complete, as with the embedding-change rule. Completion state lives in a DB `kpi_rebuild_state` table keyed by target `computation_rule_version` with `pending`/`running`/`complete`; the rolling job sets `complete` only after every company succeeds.
- A rebuild is triggered by a config change to a KPI definition, computation rule or estimation rule. It is idempotent via the storage key, runs at lower priority a few companies at a time under the existing fair-share limits, and never uses `DELETE` before recompute. Older document-version rows remain as audit/superseded history. The config change ships as its own release with both paths tested.

## Consequences

- ADR-0008's four-column PK is superseded; this ADR supplies the key that separates estimated months. The DDL in `research-neon-kpi-timeseries.md` remains a sizing sketch and its `DELETE`-before-recompute pattern is rejected.
- #353 consumes `kpi_current`; #354 consumes the after-commit `kpi.recomputed` event. Neither owns KPI row writes.
- Phase 2 tests must cover changed/added/removed figures, delta-on versus delta-off equivalence, an indirectly dependent KPI, three estimated months from one quarter, read-time conflict derivation, retention-based deletion, config gating of `computation_rule_version`, and failed-commit/no-event behaviour.
- This is a Phase 2 decision only; no KPI table, port or adapter exists in the Phase 1 as-built baseline (`docs/plans/phase1/phase1_as_built_deviations.md:132`).
