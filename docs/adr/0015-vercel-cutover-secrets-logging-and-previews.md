# ADR-0015: Vercel Hobby cutover syncs a closed web key set, forwards allow-listed logs, and isolates previews

## Status

Accepted. Consumes the Vercel Hobby research (#346, `docs/research/vercel-hobby-deployment.md`) and the as-built record (`docs/plans/phase1/phase1_as_built_deviations.md:120-121`); extends the OTLP-to-CloudWatch pattern in ADR-0006 to the web BFF. Settles #358. Exact config key names and validation stay with #359; the Vercel section of the Phase 2 spec stays with #360. No glossary change is needed: deployment tiers, secret sync, log forwarding and preview scopes are operational concepts, not domain terms.

## Context

#358 asked for the Vercel production deployment, secret synchronisation, logging hygiene, preview policy and rollback for Phase 2. The ticket prescribed an answer, but fact finding exposed four places where the prescription could not be taken literally:

- **The backend already exists in AWS production.** `docs/deployment.md:3-9` records production deployed (Stage D-7, 2026-11-18): Lambda zip packages behind an API Gateway HTTP API at `api.finsight.sahcreatives.com`, smoke-tested on every push to `main`. The pilot database is Neon with pgvector (`config/prod.yaml:12`), not Aurora paused to zero — Aurora is implemented in CDK but undeployed (`phase1_as_built_deviations.md:36-44`). Dev and staging are not deployed (`:120`), so a "staging API" for previews does not exist. The frontend is the only missing half of the cutover (`:121`). Two owner gates remain: the custom-domain CNAME may still need correcting (`docs/deployment.md:407-414`) and LLM provider keys in SSM are pending, so `/ask` currently returns the graceful `insufficient_data` envelope (`:416-428`).
- **The web env surface is small and fully known.** `web/src/lib/config/server-config.ts:86-126` reads `BACKEND_API_URL`, `BACKEND_REQUEST_TIMEOUT_MS`, `COGNITO_REGION`, `COGNITO_USER_POOL_ID`, `COGNITO_CLIENT_ID`, `AWS_REGION`, `SESSION_STORE`, `SESSION_TABLE_NAME`, `SESSION_COOKIE_NAME`, `SESSION_COOKIE_SECURE`, `SESSION_REFRESH_AHEAD_SECONDS` and `AUTH_REFRESH_TOKEN_DAYS`; there are no `NEXT_PUBLIC_*` reads and no feature flags. The production DynamoDB session table is `finsight-prod-sessions` (`infra/cdk/stacks/data.py:304-307`). Web reads no model keys, database passwords or Textract keys. There is no runtime mock backend — the BFF always proxies to `BACKEND_API_URL` (`web/src/app/api/backend/[...path]/route.ts:22-49`) — and no logger or log allow-list in web. The backend's redaction lists are Python-only and duplicated (`src/finsight/core/logging/redaction.py:8-26`, `src/finsight/adapters/tracing/_tracing_redaction.py:15-36`, `infra/otel/collector.yaml:15-35`), so the standing "one shared never-log list" does not yet exist.
- **Script and API constraints.** `scripts/` contains only Python scripts run with `uv run python` (`sync_lambda_env.py:26-28`); `web/scripts/` contains one `.mjs` file and there is no TypeScript runner at repo root, so the ticket's `scripts/sync-vercel-env.ts` was an example, not a fit. Vercel's env API supports batch upsert but documents `created`/`failed` partial results with no transaction (Vercel REST API v10), and its write-only `visibility: "secret"` values cannot be read back. `git.deploymentEnabled.main: false` disables production auto-deploy while leaving preview branches enabled, and Vercel OIDC Federation is available on Hobby, allowing a Function to exchange `x-vercel-oidc-token` via `sts:AssumeRoleWithWebIdentity` for short-lived AWS credentials. Hobby retains runtime logs for one hour and has no Log Drains, but ADR-0006 already sends backend spans to CloudWatch Logs over OTLP.
- **Enforcement language matters.** A build-time test cannot observe runtime log values, and "no partial sync" cannot mean an atomic Vercel transaction. Both terms therefore need operational definitions rather than literal ones.

The user settled every branch of the decision tree in two grilling rounds. This ADR records those answers. The baseline `make preflight` was green before any edit: 982 unit tests, 188 architecture tests, lint, types, import rules and bootstrap parity.

## Decision

- **Target and production wiring.** Deploy the Next.js frontend on Vercel Hobby at the apex `finsight.sahcreatives.com` with a Vercel-managed HTTPS certificate. Production `BACKEND_API_URL` is the live AWS API at `https://api.finsight.sahcreatives.com` (the raw `execute-api` URL until the owner-corrected CNAME resolves), with the production Cognito config and `finsight-prod-sessions`. Hobby is accepted under its limits (non-commercial use, at most 10 concurrent function executions, 300-second functions); the Pro upgrade triggers — commercial launch, more concurrency or duration, Log Drains, usage API, password-protected previews — are written into the spec and runbook rather than represented by a config switch. The pending DNS and provider keys are recorded as inherited owner gates, not as blockers for this decision.
- **Production deploys are sync-then-hook.** Set `git.deploymentEnabled.main: false` so a push to `main` does not auto-deploy production; keep PR and branch previews auto-enabled. A single merge-to-main workflow syncs secrets and then triggers a Deploy Hook. A code-only change therefore also performs an idempotent sync before it deploys. The deprecated `github.enabled: false` is not used, because it blocks Deploy Hooks.
- **Sync contract.** `scripts/sync_vercel_env.py` runs as `uv run python scripts/sync_vercel_env.py --environment prod`, reads SSM with boto3 and writes through the Vercel REST API. It reads a dedicated `/finsight/prod/web/` path containing exactly eight parameters: `BACKEND_API_URL`, `COGNITO_REGION`, `COGNITO_USER_POOL_ID`, `COGNITO_CLIENT_ID`, `AWS_REGION` (pinned — Vercel otherwise injects the function execution region), `SESSION_STORE`, `SESSION_TABLE_NAME` and `SESSION_COOKIE_SECURE`. Timeouts, cookie name, refresh-ahead and token-days keep their existing `server-config.ts` defaults and are not synced; there are no feature flags to sync. A missing or empty allow-listed key, or any unexpected key under that path, fails loudly, so a backend-only secret cannot enter Vercel by accident. No model key, database password, Textract key or other backend-only secret is ever in scope.
- **Secret visibility and failure semantics.** The eight values are stored as readable encrypted Config variables, not Vercel's write-only Secrets: Cognito client id and API URL are effectively public and the table name is an identifier, so project-member visibility is acceptable, and readability is what makes compensation possible. "No partial sync" means: preflight-read and validate all eight values, upsert them as one batch, and on any failure restore the prior values of keys already written from the preflight snapshot, block the redeploy and alert. Because the Vercel API reports partial `created`/`failed` results and offers no transaction, writes are serialized and retried with backoff on the documented concurrent-update error; where a prior value cannot be read, the script fails before writing rather than guessing. A daily scheduled workflow performs the same idempotent re-sync; it never generates or rotates credentials, which stay with their owning systems. GitHub Actions uses its OIDC role for SSM reads and a `VERCEL_TOKEN` secret for the API.
- **One shared never-log list, three enforcement levels.** `config/never_log.yaml` is the authoritative deny-list for both the Python backend and the web BFF. The web BFF emits only the eight ticket fields — `request_id`, `user_id_hash`, `company_id_hash`, `role`, `endpoint`, `status_code`, `latency_ms`, `cache_hit` — and hashed identifiers are allowed while raw company identifiers are not. A contract test fails if the web allow-list intersects the deny-list or if the two consumers disagree (the Python backend and the web vitest test both read the file). Three levels enforce this: a build-time vitest static scan of web log call sites for non-allowlisted fields and literal sensitive strings, a dev/test runtime logger that throws on a forbidden key, and a canary test with synthetic question text, document content and company identifiers proving they never reach an emitted record. The ADR records explicitly that static scanning alone cannot prove runtime absence, so the runtime check is required. Log-redaction audit (R16) remains out of scope.
- **Log forwarding.** The web BFF forwards the allowed fields directly to the CloudWatch Logs OTLP endpoint. Vercel OIDC Federation supplies `x-vercel-oidc-token`, exchanged via `sts:AssumeRoleWithWebIdentity` for temporary credentials **inside** the request handler, which SigV4-sign the OTLP POST; no long-lived AWS keys are stored in Vercel. Web logs use a separate group `/aws/finsight/web-prod` with config-driven retention (30 days in the pilot), and the IAM role is scoped to `logs:PutLogEvents` and `logs:CreateLogStream` on that group only. Delivery is non-blocking with bounded retries so logging never fails a request; repeated failures raise a CloudWatch alarm. This extends ADR-0006 rather than relying on Hobby's one-hour runtime logs; the Vercel dashboard remains a debugging convenience, not the retention source.
- **Preview policy.** Because staging is not deployed, Phase 2 previews use the mock backend only (`preview_api_target: mock`) in both pilot and standard. #359 removes `staging` from the enum and records it as a future extension gated on a real staging deployment, so there is no untestable second path. Implementation adds a narrow mock adapter behind the BFF proxy: when `mock` is selected, `/api/backend/*` returns deterministic canned responses for the endpoints the screens need (health, current-user, documents list, kpis, charts, dashboard fingerprints) with no real company data. A production build with `mock` selected fails the build, and previews never receive the production `BACKEND_API_URL`. Previews are for build plus automated smoke and a11y checks only; manual screen acceptance stays local against the prototype per ADR-0014. Vercel Standard Protection and production-scoped variables isolate them, and CI reads preview env metadata through the API, asserts no allow-listed key is scoped to preview with a production value, asserts `BACKEND_API_URL` exists only in production scope, and never prints values.
- **Rollback and ownership.** Instant Vercel rollback promotes the previous deployment; because promotion does not revert environment variables, a bad sync is rolled back by re-running the same script against last-known-good SSM values. Both paths are documented in a runbook written during implementation and linked from the spec; no runbook is authored by this planning ticket. #359 owns the concrete `web.vercel.*` keys and validation (including retention and the never-log file); #360 writes the Vercel deployment section of `docs/plans/phase2/phase2_spec.md` from this ADR.

## Consequences

- Production deploys become a single controlled path: nothing reaches `finsight.sahcreatives.com` until the full secret sync has succeeded. The cost is one extra idempotent sync on code-only merges and a Deploy Hook that must be treated as a secret URL.
- Compensating restore is best-effort, not a transaction. Readable Config variables are deliberate: if one of the eight values ever becomes a real credential it must leave this allow-list and receive a separate rotation design, because Vercel Secrets cannot be read back and cannot be compensated.
- Web logging gains retention beyond Hobby's one hour without long-lived AWS keys, at the price of a new OIDC trust, a scoped IAM role, a separate log group, and a bounded, non-blocking OTLP client in the BFF. ADR-0006's structured-log and alarm pattern is reused, not replaced.
- Previews can no longer silently call production, and the removed `staging` enum value removes an untestable path. The mock adapter is new implementation work; screen acceptance remains local, so previews are not a substitute for the ADR-0014 gate.
- Hobby remains a deliberate interim choice: commercial use, more than ten concurrent functions, functions over 300 seconds, or a need for Drains/usage API/password protection means a Pro decision, not a config switch.
- No code, config, infrastructure or prototype behaviour changes here. Implementation still needs the OIDC roles and trust policies, the sync script and its tests, the shared never-log file and parity tests, the BFF logger and mock adapter, the web workflow changes, the runbook, and the spec section.
